# Универсальный промпт для корпуса интервью-вопросов

Этот шаблон подходит для frontend, backend и других профессий. Перед запуском измените только блок «Параметры задачи», затем скопируйте весь текст внутри большой рамки в Codex или Claude Code.

Промпт рассчитан на работу внутри активной подписочной сессии агента. Он запрещает использовать API-ключи приложения, AI SDK и платные batch-запросы.

````text
# Параметры задачи — заполнить перед запуском

ROLE_KEY=<стабильный латинский ключ, например backend>
ROLE_NAME=<название профессии по-русски, например Backend-разработчик>
SPECIALIZATION=<специализация или none>
STACKS=<технологии через запятую>
FRAMEWORKS=<основные фреймворки или none>
LANGUAGE=ru
TARGET_PATH=data/question-bank/<role-key>-v1.jsonl
REPORT_PATH=reports/question-bank/<role-key>-v1-audit.md
TARGET_SIZE=<ориентир или диапазон, например 300-500; это не квота>
TOPIC_COVERAGE=<темы и желаемые пропорции; допускается скорректировать после исследования>
UPDATE_APPLICATION_SCHEMA_IF_NEEDED=true
IMPORT_TO_DATABASE=false

# Задача

Создай в текущем репозитории проверенный корпус интервью-вопросов для роли `${ROLE_NAME}` и специализации `${SPECIALIZATION}`. Результат сохрани в `${TARGET_PATH}` в формате JSONL: одна самостоятельная запись на строку. Подготовь отчёт аудита в `${REPORT_PATH}`.

Не останавливайся на плане. Сам исследуй репозиторий, источники и актуальную документацию, создай или обнови корпус, проверь его автоматическими тестами и исправь найденные проблемы. Не затрагивай несвязанные пользовательские изменения.

## 1. Финансовые и технические ограничения

- Выполняй исследование, генерацию, перевод, классификацию и рецензирование только средствами текущей подписочной сессии Codex или Claude Code.
- Запрещено читать, выводить, передавать или использовать ключи приложения и relay-секреты для этой работы, включая `OPENAI_API_KEY`, `NUXT_OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `CODEX_API_KEY` и `AI_RELAY_*`.
- Не создавай скрипты, которые импортируют OpenAI SDK, Anthropic SDK или обращаются к API AI-провайдеров. Не запускай Responses API, Chat Completions, Web Search API или другие платные batch-вызовы.
- Для поиска фактов используй встроенные средства исследования текущего агента. Если они недоступны, остановись и сообщи об ограничении. Не заменяй проверку знаниями модели по памяти.
- Обычные детерминированные скрипты для валидации JSONL, сортировки, подсчётов и проверки уникальности разрешены: они не должны обращаться к AI API и читать ключи приложения.

## 2. Сначала изучи текущий проект

До создания записей:

1. Прочитай `AGENTS.md`, `CLAUDE.md`, релевантные DTO, схему question bank, тесты корпуса и один-два существующих JSONL-объекта.
2. Зафиксируй фактический контракт полей и допустимые enum-значения. Не придумывай параллельную несовместимую схему.
3. Проверь, поддерживает ли схема `${ROLE_KEY}`, нужные фреймворки и стек. Нельзя записывать backend-вопросы с `role: "frontend"` или маскировать технологии неподходящими enum-значениями.
4. Если `UPDATE_APPLICATION_SCHEMA_IF_NEEDED=true` и текущая схема слишком узкая, сначала обобщи её и добавь точечные тесты. Не выполняй миграцию и импорт в БД, пока `IMPORT_TO_DATABASE=false`.
5. Проверь существующие корпуса. Полезные канонические записи сохраняй; не создавай их заново только ради количества.

## 3. Цель и принципы корпуса

- `${TARGET_SIZE}` — ориентир, а не обязательная цифра. Лучше меньше разных и проверенных вопросов, чем большой корпус с повторами.
- Покрой фундамент, практическую работу, диагностику, тестирование, безопасность, производительность, архитектуру, поведенческие сценарии, live coding и system design там, где это уместно для роли.
- Не подгоняй количество под заранее заданные проценты. После исследования скорректируй тематические пропорции, если это повышает качество покрытия, и объясни решение в отчёте.
- Вопрос должен проверять конкретную компетенцию и быть реалистичным для собеседования. Удаляй навигацию, рекламу, вопросы вне выбранной роли, устаревшие вопросы без учебной ценности и искусственные мелочи.
- Не копируй документацию. По официальным материалам создавай собственные вопросы и ответы, сохраняя технический смысл.
- Идентификаторы должны быть стабильными и не зависеть от порядка строк: `${ROLE_KEY}_<technology>_<concept_key>`. `slug` строится по тому же смысловому ключу.

## 4. Политика источников и лицензий

Перед импортом любого репозитория проверь `LICENSE` или другое первичное лицензионное уведомление именно на зафиксированном commit SHA. Запись в этом шаблоне — исходная подсказка, а не замена актуальной проверке.

Для каждого импортируемого материала зафиксируй:

- URL репозитория;
- commit SHA;
- SPDX-лицензию;
- путь исходного файла;
- URL конкретного источника, если он есть;
- SHA-256 хеш исходного фрагмента;
- способ обработки: `translated`, `adapted` или `original`;
- краткое описание изменений;
- необходимость атрибуции.

Политика использования:

- разрешающая лицензия с коммерческим использованием и модификацией — `direct`;
- CC-BY — `direct`, но только с требуемой атрибуцией и описанием изменений;
- отсутствие лицензии — `reference_only`;
- ShareAlike со сложной совместимостью — по умолчанию `reference_only`;
- NonCommercial или NoDerivatives — `blocked`;
- коммерческие каталоги и сайты без разрешения на перенос базы — `reference_only`;
- сомнительный источник пропусти. Не пытайся компенсировать юридическую неопределённость перефразированием.

### Проверенный frontend-пресет

Перед повторным использованием всё равно перепроверь лицензию и зафиксируй текущий commit SHA.

| Источник | Исходная политика | Назначение |
|---|---|---|
| `yangshun/front-end-interview-handbook` | MIT, `direct` | Общий frontend, JavaScript, DOM, system design, поведенческие темы |
| `lydiahallie/javascript-questions` | MIT, `direct` | JavaScript, задачи с кодом и объяснение механизмов |

Заблокированный пример: `bregman-arie/devops-exercises` с CC BY-NC-ND 3.0 нельзя использовать в коммерческом переработанном корпусе.

### Источники для других профессий

Для backend или другой технической специализации сначала составь собственный реестр официальной документации и репозиториев с разрешающими лицензиями. Не переноси frontend-список механически.

Для профессий вне разработки можно использовать как основу компетенций:

- O*NET;
- ESCO;
- открытые данные «Работы в России»;
- требования из вакансий;
- официальные профессиональные стандарты и нормативные документы.

Они помогают определить задачи и навыки, но вопросы и критерии ответа нужно создавать самостоятельно и затем проверять.

## 5. Формат JSONL

Используй фактический контракт репозитория. Если его нужно обобщить, сохрани как минимум следующую семантику:

```ts
interface QuestionCorpusItem {
  id: string;
  slug: string;
  language: "ru" | "en";
  originalLanguage: "ru" | "en";

  role: string;
  framework: string; // "none" для общих вопросов
  topic: string;
  subtopic: string | null;
  interviewType:
    | "technical"
    | "behavioral"
    | "live_coding"
    | "system_design";
  seniority: "junior" | "middle" | "senior";
  difficulty: 1 | 2 | 3 | 4 | 5;

  question: string;
  variants: string[];
  answer: string | null;
  answerFormat: "plain" | "markdown" | null;
  tags: string[]; // стек, технологии и признаки для выборки
  expectedConcepts: string[];

  status: "review";
  technicalReview: "pending" | "passed" | "rejected";
  editorialReview: "pending" | "passed" | "rejected";

  provenance: {
    sourceType: "open_source" | "official_docs" | "original";
    sourceName: string;
    repositoryUrl: string | null;
    sourceFilePath: string | null;
    sourceCommitSha: string | null;
    sourceUrl: string | null;
    licenseSpdx: string | null;
    attributionRequired: boolean;
    importType: "translated" | "adapted" | "original";
    originalContentHash: string | null;
    changesSummary: string | null;
    importedAt: string;
    answerSources: Array<{
      name: string;
      url: string;
      sourceType: "official_docs" | "standard";
    }>;
    answerVerifiedAt: string | null;
  };
}
```

Правила полей:

- `framework` обозначает основную технологическую группу; конкретный стек дополнительно отражается в `tags`.
- `variants` содержит полезные альтернативные формулировки того же вопроса, а не новые концепции.
- `expectedConcepts` перечисляет признаки сильного содержательного ответа.
- Для `open_source` обязательны `repositoryUrl`, `sourceFilePath`, `sourceCommitSha`, `licenseSpdx` и `originalContentHash`.
- Для `official_docs` обязательны `sourceName` и `sourceUrl`; текст документации не копируется.
- Если ответ нельзя подтвердить первичными источниками, оставь `answer: null`, `answerFormat: null`, `technicalReview: "pending"` и укажи запись в отчёте.
- `technicalReview: "passed"` разрешён только после независимой проверки всех существенных фактов.
- Сортировка файла: `role → framework → topic → seniority → id`.

## 6. Калибровка уровня и сложности

Оценивай минимальную устойчивую компетенцию, необходимую для полного сильного ответа. Не сохраняй прежний грейд из уважения к источнику и не подгоняй распределение под квоту.

### Junior

- Фундамент и применение одного базового понятия в типовой ситуации.
- Не требует production-опыта, проектирования процессов, архитектурных компромиссов, продвинутой диагностики или знания внутренних механизмов.
- `difficulty` только 1–2.
- System design не может быть Junior.

### Middle

- Уверенное практическое применение нескольких связанных понятий.
- Отладка, тестирование, состояние, интеграции, базовая производительность и безопасность.
- Знание назначения CI/CD допустимо, но проектирование pipeline, quality gates и стратегии релиза уже выше Junior.
- `difficulty` 2–4.

### Senior

- Проектирование систем и процессов, оценка компромиссов и рисков.
- Масштабирование, глубокая безопасность и производительность, observability, архитектура CI/CD, релизы и сложные production-инциденты.
- `difficulty` 4–5.

Поведенческие вопросы классифицируй по масштабу требуемой ответственности. Live coding — по сложности решения, ограничениям и необходимым граничным случаям.

После основной классификации отдельно и консервативно перепроверь все Junior-вопросы. Если сильный ответ обычно требует коммерческого production-опыта, повысь уровень.

## 7. Дедупликация и канонизация

Веди глобальный индекс концептов по всему корпусу. Нельзя проверять дубли только внутри текущего пакета.

1. Найди точные совпадения после нормализации регистра, `ё/е`, пунктуации и пробелов.
2. Сравни ключевой концепт, `expectedConcepts`, теги и содержание сильного ответа.
3. Считай вопросы смысловыми дублями, если сильный кандидат дал бы на них по существу один и тот же ответ с той же глубиной.
4. У одного концепта оставь одну каноническую запись на роль, технологический контекст и грейд.
5. Лучшую формулировку выбери по ясности и естественности. Остальные полезные формулировки перенеси в `variants`.
6. Не объединяй вопросы только из-за общего тега. Разные аспекты одной технологии, разные компромиссы и разные уровни глубины могут быть самостоятельными вопросами.
7. Один концепт допустим на разных грейдах только при реальном различии глубины: базовое определение для Junior, практические решения для Middle, архитектурные компромиссы для Senior.
8. Если сомневаешься, зафиксируй пару в отчёте для ручной проверки, но не удаляй запись без обоснования.

## 8. Перевод, Humanizer и редактура

- Для английских и неестественно сформулированных материалов примени Humanizer RU или эквивалентную русскоязычную редактуру. Humanizer не должен добавлять факты или менять технический смысл.
- Готовый качественный русский текст сохраняй, исправляя только доказуемые ошибки и фиксируя изменение в `changesSummary`.
- Английский материал переводи технически точно, затем редактируй естественный русский текст.
- Убирай кальки, канцелярит, рекламный тон, искусственные перечисления, одинаковый ритм и лишние вводные фразы.
- Не добавляй факты и не меняй степень уверенности исходного материала ради более гладкого текста.
- Устойчивые термины вроде `event loop`, `tree shaking`, `hydration`, `type narrowing`, `backpressure` или `eventual consistency` оставляй рядом с понятным русским названием, если перевод без оригинала может быть неоднозначным.
- Сохраняй код, идентификаторы, команды, URL и синтаксис без типографических замен.

## 9. Подготовка и проверка ответов

Для каждого вопроса сначала проверь существенные факты по актуальной официальной документации, спецификации, стандарту или другому первичному источнику.

- Не используй блоги, форумы, коммерческие каталоги и память модели как доказательство.
- Ответ должен быть самостоятельным, точным и естественным: обычно 2–5 предложений без вводной воды.
- Если вопрос требует кода, добавь минимальный корректный пример.
- Не вставляй ссылки и служебные сноски внутрь `answer`.
- В `provenance.answerSources` сохрани 1–3 прямые HTTPS-ссылки на первичные источники.
- Удаляй tracking-параметры из URL.
- Не утверждай, что ответ проверен, если хотя бы один существенный факт остался неподтверждённым.

После первого прохода выполни независимую рецензию. Не доверяй готовому ответу и заново проверь факты. Обязательно включи в критическую выборку:

- безопасность и приватность;
- версии API и изменившееся поведение;
- ограничения браузеров или платформ;
- SSR, hydration и конкурентность;
- реактивность и управление состоянием;
- производительность и масштабирование;
- архитектурные компромиссы;
- все вопросы system design;
- Senior-вопросы по основным фреймворкам и стеку.

Исправление опиши в `changesSummary`. Если исходный ответ корректен, не переписывай его ради стилистического разнообразия.

## 10. Порядок выполнения

1. Составь реестр источников с политикой `direct`, `reference_only` или `blocked`.
2. Определи тематическое покрытие без жёсткой квоты.
3. Импортируй только разрешённые материалы с полной provenance-информацией.
4. Допиши оригинальные вопросы по официальной документации для недостающих тем.
5. Проведи глобальную канонизацию и дедупликацию.
6. Откалибруй seniority и difficulty, затем отдельно перепроверь Junior.
7. Подготовь ответы и первичные источники.
8. Выполни независимую техническую рецензию критических вопросов.
9. Проведи русскую редактуру и проверь сохранность кода и терминов.
10. Отсортируй JSONL и запусти проверки.
11. Сформируй один отчёт `${REPORT_PATH}`. Не создавай второй контентный файл.

Обрабатывай большой корпус небольшими проверяемыми группами, но поддерживай единый глобальный индекс концептов и прогресса. Не запускай несколько слепых повторных проходов: сначала выясняй причину ошибки, затем исправляй только нужные записи.

## 11. Автоматические проверки

Добавь или обнови точечные тесты, которые проверяют:

- валидность каждой JSONL-строки;
- обязательные поля и enum-значения;
- уникальность `id` и `slug`;
- отсутствие точных нормализованных дублей;
- допустимые диапазоны difficulty для каждого грейда;
- запрет system design для Junior;
- корректные HTTPS-URL;
- provenance и commit SHA у импортированных материалов;
- наличие источников у каждого подтверждённого ответа;
- согласованность `answer`, `answerFormat` и `technicalReview`;
- сортировку файла;
- отсутствие записей из `reference_only` и `blocked` источников.

Смысловые дубли, естественность языка и корректность технических ответов нельзя считать доказанными одним автоматическим тестом: проверь их содержательно средствами текущей подписочной сессии.

## 12. Отчёт и критерии приёмки

В `${REPORT_PATH}` укажи:

- итоговое количество вопросов без сравнения с искусственной квотой;
- распределение по темам, стеку, типу интервью и грейду;
- разрешённые, отклонённые и reference-only источники;
- лицензии и требования атрибуции;
- количество объединённых смысловых дублей и причины;
- количество вопросов с подтверждёнными ответами;
- список вопросов без ответа или с незавершённой проверкой;
- изменения грейдов и причины спорных решений;
- команды проверок и их фактический результат.

Работа принята, если:
````
