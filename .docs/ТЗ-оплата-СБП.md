# ТЗ: Приём оплаты через СБП (Систему быстрых платежей)

Статус: утверждено 2026-07-11 (решение владельца по разделу 3 — Уровень 1); реализовано 2026-07-11 (бэкенд `confirmation.type=embedded`, DTO, нативное всплывающее окно виджета ЮKassa через `customization.modal=true`, composable `useYookassaWidget.ts`, тесты; СБП в тестовом виджете ЮKassa недоступна).

Замечание по реализации: в нативном modal-режиме виджет инициализируется с `customization: { modal: true }`, а `render()` вызывается без id контейнера. Событие `modal_close` возвращает пользователя к форме чекаута.

## 0. Принципиальные решения

- **Уровень интеграции — Уровень 1, виджет ЮKassa (решение владельца).** После создания платежа наша оболочка чекаута скрывается, а виджет открывает собственное всплывающее окно, без редиректа на чужой домен и без самописного QR.
- **Нативное окно ЮKassa, не модалка внутри модалки.** Отдельная `/pricing/sbp`-страница не нужна.
- **Логотип СБП в футере сайта — не требуется.** Правило НСПК «добавить лого СБП в подвал» действует только «если в подвале уже есть логотипы других способов оплаты» (стр. 37 брендбука). Проверено: ни в `apps/landing/components/landing/TheFooter.vue`, ни в основном приложении логотипов способов оплаты сейчас нет вообще — значит и лого СБП добавлять не нужно.
- **Для dev используем тестовый магазин GLASNO (shopId `1408058`).** Он изолирует тестовые платежи и вебхуки от Mentala, но не даёт проверять СБП: это общее ограничение тестовых магазинов ЮKassa, см. раздел 8.
- **Событие вебхука `payment_method.active` — не включать.** Текущий обработчик вебхука не рассчитан на него и будет на нём падать с ошибкой валидации (не критично, но шумно и бессмысленно). См. раздел 9.

## 1. Контекст

По письмам ЮKassa для `ShopID 1404198` (боевой магазин `my.glasno.app`):

- Способ оплаты API ЮKassa подключён, заявление одобрено, договор об ИТВ заключён.
- СБП отдельно подключена для этого же `ShopID`. Выданы `LegalID = LA0005162880`, `MerchantID (ТСП в СБП) = MB0003034588`, `МСС = 7372`. Это исключительно регистрационные идентификаторы на стороне ЮKassa/НСПК — в коде и env они не используются и никуда прописывать их не нужно.
- Требование НСПК: там, где показываем/объясняем СБП, использовать графику и тексты из официального брендбука, с поправками под свой стиль, если что-то не совпадает.

## 2. Что уже работает без единой строчки кода

Текущий чекаут (`server/api/billing/checkout.post.ts` → `billingService.createCheckout` → `yookassaClient.buildYooKassaCreatePaymentRequest`) создаёт платёж с `confirmation.type: 'embedded'` **без** `payment_method_data` и без ограничения `customization.payment_methods`. Поэтому встроенный виджет ЮKassa сам показывает все способы, доступные конкретному ShopID. Для боевого `ShopID 1404198` API возвращает `sbp` в списке `payment_methods`, поэтому в production виджет покажет отдельную плитку СБП.

Это подтверждает и текст, который уже лежит в `app/i18n/locales/ru.json:758`: «Карта, СБП и другие способы через YooKassa» — он был написан на будущее и теперь стал верным.

Также уже корректно обработан нюанс: СБП-платёж не возвращает сохраняемый `payment_method` (в отличие от карты), поэтому автопродление для него не активируется — это уже учтено комментарием в `server/infrastructure/billing/drizzleBillingRepository.ts:1090` и логикой `save_payment_method`. Дополнительно ничего чинить не требуется.

## 3. Варианты глубины интеграции

Как это устроено у аналогов (Ozon, Wildberries, банковские/подписочные сервисы): СБП показывается как отдельная плитка способа оплаты рядом с картой; при выборе — на десктопе QR-код с таймером и кнопкой «Я оплатил», на мобильном — список банковских приложений (deep link) без QR. Ни один из известных сервисов такого масштаба не рисует список банков и QR вручную — это делает провайдер эквайринга (аналог ЮKassa на их стороне), потому что список банков-участников СБП периодически меняется и его самостоятельная поддержка — постоянная обуза.

| | Уровень 0 — как сейчас (redirect) | **Уровень 1 — embedded-виджет ЮKassa (рекомендую)** | Уровень 2 — полностью свой UI |
|---|---|---|---|
| Что делаем | Ничего | Встраиваем `checkout-widget.js` в `BillingCheckoutModal.vue` вместо перехода на `confirmationUrl` | Создаём платёж с `payment_method_data.type: 'sbp'` + `confirmation.type: 'qr'`, сами рисуем QR и статус-поллинг |
| Ощущение для пользователя | Уходит на страницу ЮKassa (другой домен/бренд) | Остаётся в Гласно; всю платёжную форму, её окно, QR и список банков рисует ЮKassa | Полностью в стиле Гласно, включая сам QR |
| Кто обеспечивает соответствие брендбуку НСПК (стр. 70–74: размеры QR, охранные поля, версии лого) | ЮKassa (их ответственность) | ЮKassa (их ответственность) | **Мы** — нужно самим соблюсти все требования из раздела 5 |
| Поддержка списка банков/deep-linked приложений | ЮKassa | ЮKassa | Мы (нужно опрашивать статус платежа, обрабатывать протухание QR через ~15–20 мин) |
| Трудозатраты | 0 | Небольшие: подключить скрипт, заменить редирект на инициализацию виджета в модалке, обработать `success`/`error` колбэки | Существенные: свой рендер QR-кода по спецификации, поллинг статуса, обработка истечения, тестирование на реальных банковских приложениях |
| Риск | Внешний вид ЮKassa не совпадает со стилем Гласно | Минимальный | Больше всего точек отказа (истечение QR, форматирование, будущие изменения API) |

**Решение владельца: Уровень 1.** Даёт нативное ощущение (пользователь не покидает Гласно) при минимальных трудозатратах и без необходимости самим соответствовать графическим требованиям брендбука НСПК — этим по-прежнему занимается ЮKassa внутри виджета. К Уровню 2 можно вернуться позже, если понадобится 100% визуальное соответствие фирменному стилю Гласно вплоть до самого QR.

## 4. UI/UX

- Точка входа не меняется: пользователь по-прежнему нажимает `pricing.checkoutCta` в `BillingCheckoutModal.vue`.
- При Уровне 1: вместо `window.location.href = confirmationUrl` инициализируем виджет с `customization.modal=true` и вызываем `render()` без контейнера. Наша модалка на время оплаты скрывается. Способ оплаты (карта/СБП/SberPay и т.д.) пользователь выбирает в нативном окне ЮKassa.
- Для внешнего вида передаём в виджет все шесть поддерживаемых цветов: `background`, `text`, `border`, `control_secondary`, `control_primary`, `control_primary_content`. Палитра выбирается по теме GLASNO. ЮKassa не даёт API для управления позицией, радиусом или геометрией нативного окна.
- СБП в виджете: на desktop ЮKassa показывает QR-код, на реальном мобильном устройстве после выбора СБП он сам открывает список банков и платёжных сервисов. Принудительно выводить этот список на desktop API виджета не позволяет.
- Отдельная страница `/pricing/sbp` не создаётся ни при каком варианте — избыточна, раз всё помещается в существующую модалку.
- Текст-анонс в модалке (`app/i18n/locales/ru.json:758`) не требует изменений — уже корректен.

## 5. Брендинг СБП (по брендбуку НСПК)

Актуально только если реализуем Уровень 2 (свой UI); при Уровне 0/1 за это отвечает ЮKassa.

- **Экран выбора способа оплаты** (стр. 38): если показываем свой список методов — плитка СБП должна быть той же высоты, что у других иконок (карта/Google Pay и т.п.), не мельче.
- **Экран-инструкция при выборе СБП** (стр. 39): три шага фиксированным текстом — выбрать СБП и подтвердить заказ → выбрать банк из установленных на телефоне → авторизоваться в приложении банка и оплатить.
- **QR-код** (стр. 71–73): изображение QR не менее 35×35 мм (при печати) с читаемостью с 30 см; для экрана — эквивалентный по факту размер, ЮKassa обычно рекомендует не менее ~200×200 px. Логотип СБП поверх QR — в пропорциях 1:4 по вертикали и 1:3 по горизонтали от QR, охранное поле ≥2,5 мм. Три версии логотипа: цветная (основная), монохромная (ограниченная печать), чёрная (только для чеков в одну краску) — в вебе нужна цветная.
- **Логотипы СБП**: ЮKassa обещала прислать архив с лого в разных цветовых моделях отдельным письмом — этого архива в текущем сообщении нет, нужно приложить отдельно, когда будет.
- Футер — не трогаем (см. раздел 0).

## 6. Технические детали (для Уровня 1)

- Подключить `<script src="https://yookassa.ru/checkout-widget/v1/checkout-widget.js">`.
- `checkout.post.ts`/`billingService.createCheckout` при этом варианте должен создавать платёж с `confirmation.type: 'embedded'` вместо `'redirect'` и возвращать `confirmation.confirmation_token` вместо `confirmation_url` (в `yookassaClient.ts:98-102` и в `shared/dto/billing.ts` — DTO ответа чекаута потребует нового поля).
- Фронт: `BillingCheckoutModal.vue` инициализирует `new window.YooMoneyCheckoutWidget({ confirmation_token, return_url, error_callback })` вместо текущего `window.location.href = response.confirmationUrl`.
- `return_url` и последующая сверка статуса (`checkout-status.get.ts` → `reconcileYooKassaCheckout`) не меняются — это общий путь и для редиректа, и для виджета.
- Для Уровня 2 отдельно: `payment_method_data: { type: 'sbp' }` + `confirmation: { type: 'qr' }`, ответ содержит `confirmation.confirmation_data` — строку, которую нужно самостоятельно отрендерить в QR (например, через `qrcode`-библиотеку), плюс поллинг статуса платежа с интервалом (у ЮKassa QR для СБП обычно живёт ограниченное время, после истечения нужно создавать новый платёж).

## 8. Нужен ли отдельный тестовый магазин для Гласно?

**Уже создан для изоляции dev-платежей, но не для проверки СБП.**

1. `.env.development` использует `NUXT_YOOKASSA_SHOP_ID=1408058` — тестовый магазин «Test (2), my.glasno.app». Это корректная конфигурация для безопасных dev-платежей.
2. Тестовый магазин ЮKassa проверяет общую механику (создание платежа → виджет → подтверждение → сверка статуса), но не позволяет проверить СБП. По документации ЮKassa в тестовом виджете доступна только оплата банковской картой; плитка ЮMoney может отображаться, но не используется для оплаты. `GET /v3/me` для `shopId=1408058` возвращает `test: true` и методы `yoo_money`, `bank_card`; принудительное `payment_methods: ['sbp']` не включит СБП, а оставит виджет без доступных способов оплаты.
3. Отдельный магазин GLASNO позволяет не смешивать вебхуки и платёжные данные с Mentala. При этом источник истины в коде — не вебхук, а активная сверка статуса через API (`reconcileYooKassaCheckout`, `syncPendingPaymentMethod`), вызываемая из `checkout-status.get.ts` и `/api/billing/status`.

Создание другого тестового магазина не решит проверку СБП: ограничение одинаково для тестовых магазинов ЮKassa. Отдельный test-shop имеет смысл только для изоляции staging-вебхуков.

## 9. Какие события вебхука нужны

На третьем скриншоте («Настройки уведомлений») включены: `payment.succeeded`, `payment.waiting_for_capture`, `payment.canceled`, `refund.succeeded`. Выключено: `payment_method.active`.

**Текущий набор — верный, `payment_method.active` включать не нужно.** Причины:

- Обработчик `handleYooKassaWebhook` в любом случае не доверяет телу вебхука и перепроверяет платёж через `GET /payments/{id}` — конкретный набор событий влияет только на то, «стоит ли вообще перепроверять», а не на корректность.
- Привязка карты без платежа (флоу «включить автопродление без карты», `startPaymentMethodBinding`) вообще не слушает вебхуки — она сверяется оппортунистически через `syncPendingPaymentMethod` при каждом обращении к `/api/billing/status`. То есть событие `payment_method.active` сейчас просто не используется никаким кодом.
- Хуже того: если его включить, ЮKassa начнёт слать на `POST /api/billing/webhook/yookassa` событие с `object`, у которого нет поля `status` в том виде, как ожидает `extractYooKassaPaymentEvent()` (`server/application/billing/yookassaClient.ts:347-368`) — парсер бросит `E_VALIDATION`, обработчик ответит ошибкой, ЮKassa будет ретраить и копить неудачные доставки в логах без какой-либо пользы. Включать это событие стоит только вместе с доработкой обработчика (отдельная ветка для `payment_method.*`), а сейчас в этом нет необходимости.

## 10. Webhook URL — нужно ли где-то настраивать на стороне ЮKassa

**Да, обязательно**, и это отдельное действие от env-переменной. `YOOKASSA_WEBHOOK_URL` в `.env.*` — это просто заметка для разработчика, приложение её никогда не читает. Реальная настройка — в личном кабинете ЮKassa, в разделе уведомлений конкретного магазина (это и есть форма со второго скриншота — «URL для уведомлений» + чекбоксы событий + «Сохранить»).

Для `ShopID 1404198` туда нужно вписать: `https://my.glasno.app/api/billing/webhook/yookassa`.

Если это ещё не настроено — приложение всё равно будет работать (см. раздел 8, источник истины — активная сверка статуса), но без вебхука подтверждение платежа будет происходить с задержкой (пока пользователь не откроет страницу возврата / не обновит статус), а не мгновенно по push от ЮKassa. Настроить стоит сразу, это 30 секунд в кабинете.
