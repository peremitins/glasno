# Serena: рабочий порядок

## Правила навигации (для агентов)

- Начинай навигацию с symbol/reference-инструментов Serena. Не читай `.vue` целиком, если достаточно overview и точечного чтения символа.
- Перед изменением shared DTO, Pinia store, composable или API-слоя сначала проверь definition и references.
- Markdown в `.docs/` читай и ищи обычными средствами: Serena для него не требуется.
- **`find_referencing_symbols` видит только ссылки через явный `import`.** Всё без import-строки для него невидимо — три слепых класса (auto-import composables/utils, Vue-компоненты в `<template>`, смешанные символы с частичным результатом); детали и замеры — в разделе «Известное ограничение» ниже. Перед удалением/переименованием/выводом «не используется» **обязательно** добивай `search_for_pattern` по имени (`substring_pattern: "\bимяФункции\b"`). Частичный результат так же ненадёжен, как пустой. Для символов с явным `import` (Pinia store, shared DTO, server-модули) — работает корректно, доп. проверка не нужна.
- Строковые маршруты, HTTP/runtime-связи и прочие dynamic imports тоже вне LSP-цепочки — подтверждай их исходниками и targeted-тестами.
- Этап 1: Serena работает в `read_only: true`. Инструменты записи не использовать. Переименование допускается только на этапе 2, сначала в preview, затем с `pnpm typecheck`.

## Архитектура: один общий сервер (shared streamable-http)

Serena работает как **единый долгоживущий HTTP-сервер**, а не как stdio-процесс на каждый чат. Причина: при stdio каждый чат/агент Codex и Claude Code порождает собственный процесс Serena + набор LSP, и на macOS они превращаются в orphan-процессы с ростом памяти до десятков ГБ (issue oraios/serena #1367, #944). Официальная рекомендация для мультиагентной работы над одним проектом — shared streamable-http инстанс.

- **Сервер**: `serena start-mcp-server --transport streamable-http --host 127.0.0.1 --port 9121 --project <glasno> --context ide`.
- **Автозапуск**: LaunchAgent `~/Library/LaunchAgents/app.glasno.serena.plist` (шаблон — `.docs/serena-launchagent.plist`). `RunAtLoad` + `KeepAlive`: сервер стартует при входе в систему и перезапускается при падении. Запускать вручную ничего не нужно.
- **MCP-эндпоинт**: `http://127.0.0.1:9121/mcp`.
- **Дашборд** (диагностика/логи): `http://127.0.0.1:24282/dashboard/` — открывать по желанию, наружу данные не уходят.
- **Контекст `ide`**: убирает дублирующие file/shell-инструменты (их предоставляют сами Codex/Claude Code), оставляет символьную навигацию — нейтрален для обоих клиентов.

Один процесс обслуживает **все** чаты и агентов обоих клиентов, с общим индексом и LSP. Проект зафиксирован (`--project glasno`), поэтому отдельная Serena-активация проекта в сессии не нужна.

### Подключение клиентов

- **Claude Code** — `.mcp.json` (project-scoped): `{ "type": "http", "url": "http://127.0.0.1:9121/mcp" }`.
- **Codex App** — пользовательский `~/.codex/config.toml`: `[mcp_servers.serena]` → `url = "http://127.0.0.1:9121/mcp"`. В актуальной установленной версии App (`codex-cli 0.144.0-alpha.4`) её единый `app-server` не загружает project-scoped `.codex/config.toml`, хотя CLI из корня проекта его видит. Поэтому эту запись нельзя переносить в project config до исправления поведения App.

Сервер будет отображаться и в других репозиториях Codex, но это не создаёт второй индекс или процесс: URL указывает на единственный инстанс, жёстко закреплённый за Glasno. Вне Glasno его не использовать.

### Принятие подключения в Codex App

После изменения пользовательского `~/.codex/config.toml` полностью перезапусти Codex App. Обычный новый чат недостаточен: App не перечитывает список MCP-серверов на лету.

1. Закрой Codex App (`Cmd+Q`) и открой его снова.
2. Введи `/mcp` и проверь, что сервер `serena` включён.
3. Попроси агента вызвать `initial_instructions`, затем `get_symbols_overview` для `app/stores/auth.ts`.
4. Подключение принято только если оба вызова вернули результат. Ответ HTTP `200` у endpoint подтверждает здоровье сервера, но не регистрацию инструментов в клиенте.

Это одноразовый acceptance-тест после настройки. `initial_instructions` **не запускает сервер** и его не нужно вводить вручную после перезагрузки компьютера или App. LaunchAgent запускает сервер сам; Codex получает требование вызвать `initial_instructions` от MCP во время инициализации и должен выполнить его один раз в своей новой MCP-сессии перед первой семантической операцией.

Если `serena` не отображается после полного перезапуска, проверь `launchctl print gui/$(id -u)/app.glasno.serena` (`state = running`) и `~/.codex/config.toml`. После этого снова выполни `/mcp`.

### Управление сервером

```bash
# статус
launchctl list | grep glasno
lsof -nP -iTCP:9121 -sTCP:LISTEN

# перезапуск (после смены версии Serena / project.yml)
launchctl unload ~/Library/LaunchAgents/app.glasno.serena.plist
launchctl load -w ~/Library/LaunchAgents/app.glasno.serena.plist

# логи
tail -f ~/Library/Logs/serena-glasno.err.log
```

> Один сервер = один проект. Для другого репозитория нужен отдельный сервер на другом порту, а не переиспользование этого.

## Известное ограничение: find_referencing_symbols видит только ссылки через явный import

Подтверждено 2026-07-12 (батарея тестов на реальных символах). `find_referencing_symbols` находит только те ссылки, где символ подключён явным `import`. Ссылка без import-строки для него невидима. Точная граница по результатам замеров:

**Работает корректно (✅):**

- Explicit import в любом направлении: `.ts`→`.ts`, `.ts`→`.vue`, `.vue`→`.ts` (`useAuthStore`, `buildManualInterviewSource`, `grantPaidAccess` — все ссылки найдены).
- Внутрифайловые ссылки внутри `.vue` (`formatDate` в `profile.vue` — обе ссылки найдены).
- `find_symbol` (поиск **определения**) для auto-import символов — работает; сломан именно поиск **ссылок**.

**Слепые зоны (❌) — три подтверждённых класса:**

| Символ (тест) | Реально ссылок | Serena нашла | Класс |
|---|---|---|---|
| `useAPI` | 21 | `{}` | чистый auto-import → пусто |
| `useBillingStatus` | 3 (1 explicit + 2 auto) | **1** | смешанный → **частично** |
| `ButtonLoader` | 10+ (в `<template>`) | `No symbol found` | Vue-компонент → не резолвится |

**Самый опасный — смешанный класс:** результат непустой, но неполный. Правдоподобный частичный список не вызывает подозрений, поэтому правило «пустой = перепроверь» здесь не срабатывает. Fallback (в `AGENTS.md`/`CLAUDE.md`): перед деструктивным действием всегда добивать `search_for_pattern`/grep; в слепых зонах текстовый поиск надёжнее символьного.

**Замер токен-экономики (зачем Serena нужна, несмотря на баг):** overview структуры вместо чтения файла целиком — `profile.vue` ~5900→~650 ток. (−89%), `interview/[id].vue` ~28 300→~3K ток. (−87%); точечное чтение символа `grantPaidAccess` ~10 300→~2100 ток. (−79%). Экономия только когда нужен обзор/один символ; при чтении файла целиком выигрыша нет. Главная ценность — не деньги, а разгрузка контекстного окна.

**Корневая причина слепых зон (двухслойная):**

1. **Баг в solidlsp** (обёртка Serena над LSP): `vue_language_server.py::_find_tsconfig_for_file` ищет `tsconfig.json`, поднимаясь от файла вверх по дереву, и берёт первый найденный — не умеет в solution-style tsconfig с `references`. Для `app/`, `server/`, `shared/` это всегда даёт корневой `tsconfig.json` (`"files": []`, только `references` на `.nuxt/tsconfig.{app,server,shared}.json`), а не реальный Nuxt-подпроект. Митигация — редирект-файлы `app/tsconfig.json`, `server/tsconfig.json`, `shared/tsconfig.json` (`{"extends": "../.nuxt/tsconfig.*.json"}`), уже добавлены в репозиторий: заставляют наивный поиск сразу попадать в верный конфиг.
2. **Архитектурное ограничение Volar** (не лечится на нашей стороне): companion TypeScript-сервер, которым `@vue/language-server` пользуется для cross-file references, запускается с флагом `--useInferredProjectPerProjectRoot` (жёстко зашит в сам `@vue/language-server`, не настраивается через Serena). В этом режиме tsserver строит программу через обход графа импортов от открытых файлов, а не через `include` из tsconfig — поэтому глобальные ambient-декларации Nuxt (`.nuxt/types/imports.d.ts`, где `useAPI` объявлен как `const useAPI: typeof import(...)`) не попадают в программу, и связь «вызов → определение» не прослеживается.

Из-за (2) фикс `app/tsconfig.json` из п.1 **не решает** проблему полностью (проверено эмпирически после чистого рестарта сервера) — но остаётся правильным сам по себе и не мешает. Реальный фикс требует правок в `@vue/language-server` (Volar) или solidlsp; отслеживать/репортить: [oraios/serena](https://github.com/oraios/serena/issues).
